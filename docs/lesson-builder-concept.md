Из этого следуют два свойства, которые обязана учитывать сверка (блок 3):

1. **Канон — часто цепочка, а не значение.** `$s = 2\pi\Delta R = 2575\text{ км}$` — ответ

   символьная эквивалентность.

## 1. Блок 1. Модель данных Урока и Блоков (эволюция `Assignment`)

### 1.1. решение

`Assignment` остаётся единицей «урок». Второй верхнеуровневой модели (`Lesson`) не
заводим: у неё были бы те же поля teacher/subject/students, и банк запросов к ним
пришлось бы писать дважды, а ученику потом объяснять, чем «урок» отличается от
«назначения». Слово «Урок» — уровень интерфейса, `Assignment` — уровень базы.

Набор задач перестаёт быть одним списком и становится четырьмя именованными частями:

```
Assignment (Урок)
  title, subject, teacher, created_at           — как сейчас
  status: draft | active | revoked              — draft добавляем (см. 2.1)
  group: FK StudyGroup | null                   — добавляем
  due_at: datetime | null                       — добавляем
  difficulty                                    — остаётся, помечен legacy (см. 1.4)
  question_ids                                  — остаётся, legacy-чтение (см. 1.5)

AssignmentBlock (Блок урока)
  assignment: FK Assignment, related_name='blocks'
  kind: in_class | homework | advanced | simplified
  title: строка                                 — «Классная работа», «Домашка», …
  order: PositiveSmallIntegerField              — порядок блоков внутри урока
  question_ids: JSONField(default=list)         — список frozen, порядок = order задач
  unique: (assignment, kind)
```

| `kind` | Русская подпись | Зачем этот блок |
|---|---|---|
| `in_class` | Классная работа | Решается вместе, на уроке; проверка не обязательна |
| `homework` | Домашка | Основная проверяемая часть; именно её процент уходит в GetCourse (блок 4) |
| `advanced` | Сложные / со звёздочкой | На запас и на сильных; банк для этого — `difficulty='hard'` + Рустюмова «БЛОК 4», Сканави «Группа В» |
| `simplified` | Упрощённые / подводящие | На тех, кто не тянет уровень; банк — `easy` + Рустюмова БЛОКИ 1–3 |

### 1.2. Порядок задач

Порядок — позиция в `question_ids` блока, ровно как в текущем `Assignment.questions`
(свойство обходит список, а не полагается на сортировку БД). Отдельного поля `position`
не заводим: `TestSessionQuestion.position` нужен потому, что сессию набирает машина и
строки существуют до чтения; здесь список пишет человек экраном, и порядок в нём —
единственный источник истины. Перестановка = PATCH блока.

`kind` + `order` вместо произвольных названий блоков — сознанно: четыре блока покрывают
назначения из реальной практики центра, а конструктор свободных блоков потребовал бы
решать, чем «блок 3» отличается от «домашки», на каждый урок заново. Если четвёрки не
хватит — это отдельное решение владельца, не имплементационная деталь.

### 1.3. Как тренер набирает блоки

Тот же `pick`, но на блок: `GET /api/assignments/pick/?subject=&difficulty=&topic=&grade=&count=`.
Фильтр по `grade` в банке уже есть (коммит `1bf915e`), фильтр по теме/`source_type` — есть
в `_pool`. Чего в пуле нет и что нужно блоку 1 в первую очередь: **фильтр по книге** —
`book` лежит в `provenance` и SQL-фильтром не берётся. Дешёвый путь — фильтровать по теме
(имя темы уже начинается с книги), честный — вынести `book` в отдельное поле строки;
это решение оставляем за ним, в документе оно не реализовано.

### 1.4. Что делать с `Assignment.difficulty`

Смысл поля (одна ступень на весь набор) ломается в момент, когда набор становится
четырёхблочным: «сложные» и «упрощённые» — это и есть ступени, только разложенные по
блокам. Предлагаемое решение: поле остаётся в схеме как **историческая метка основного
набора**, экран его больше не спрашивает, новый UI опирается на блоки. Удалять поле
сейчас не за чем: миграция на удаление — лишний шаг на проде без выигрыша.

### 1.5. Обратная совместимость

Прод и локаль содержат по **0 строк** `Assignment` (замер 14.10), поэтому миграции данных
нет. Что нужно заложить в схему, чтобы она осталась честной, если он создаст назначение
до правки модели:

* `AssignmentBlock` — таблица; у строки без блоков чтение даёт один виртуальный блок
  `homework` из `question_ids`. Это единственная совместимость, и она живёт ровно до
  первого редактирования урока.
* `question_ids` на `Assignment` не удаляем в той же миграции, что и вводим блоки.
* Свойство `Assignment.questions` продолжает работать и не должно сломаться — на него
  опирается `AssignmentDetailSerializer`.

## 2. Блок 2. Жизненный цикл ДЗ и сохранение результатов

### 2.1. Состояния урока

```
draft ──опубликовать──> active ──срок вышел──> active + закрыт по due_at
  │                        │
  └─(не виден никому)      └──отозвать──> revoked   (след остаётся, как сейчас)
```

Сегодня `Assignment` рождается сразу в `active` — экран «Назначение по уровню» не знает
черновика. Для конструктора это обязательно: урок собирается в четыре блока несколько
минут, и всё это время ученик не обязан получать недособранный набор. Поэтому
`status` получает значение `draft`, и публикация — явное действие (кнопка «Опубликовать»),
а не побочный эффект `POST /assignments/`.

### 2.2. Модели результатов

```
AssignmentSubmission (одна на ученика, урок и блок)
  block: FK AssignmentBlock | null             — по какому блоку сдаёт (in_class могут не сдавать)
  student, assignment
  state: in_progress | submitted | reviewed
  started_at, last_submitted_at, reviewed_at, reviewed_by
  unique: (assignment, student, block)

AssignmentAnswer (одна строка на сдачу одной задачи)
  submission: FK AssignmentSubmission
  question: FK Question
  raw_answer: TextField                        — что ученик набрал/вставил, как есть
  normalized_answer: TextField                 — то, что из него вычленил нормализатор (0 ₸)
  verdict: correct | partial | incorrect | pending_review
  points_earned, points_max: Float
  judged_by: level1 | cas | model_suggestion | human   — чем решён вердикт
  created_at, updated_at
  unique: (submission, question)
```

Что здесь принципиально:

* **`raw_answer` неизменяем.** Правка — новая строка/новая версия, а не перезапись:
  «ученик так написал» должно быть видно тренеру, когда он ставит `partial`.
* **`verdict` — четыре значения, а не булев.** У открытых задач неверный ответ и
  нерешённая задача — разные события; `pending_review` — это не «0», а «ещё не проверено».
* **`judged_by` обязателен.** Он реализует правило «слову модели не верим» в данных:
  если вердикт выставила модель, он не может выглядеть как машинная проверка, и
  следующий перегон/экран обязан это видеть (ср. `accepted_mode: "auto"` в банке).
* **Историю попыток (пересдачи) пока не заводим.** У `AnswerRecord` её тоже нет, и
  ученику она не нужна; отдельная таблица понадобится, если включим пересдачи.

### 2.3. Экран (а): методист/тренер — сборка и матрица результатов

```
/teacher/lessons                      — список уроков (+ черновики), кнопка «Новый урок»
/teacher/lessons/<id>                 — конструктор: 4 колонки-блока

  [фильтр банка: предмет | тема/книга | класс 5..11 | сложность | статус приёмки]
        ↓  GET /api/questions/?subject=&topic=&grade=&difficulty=&verification_status=
  [список задач: чекбокс + «в Классную / в Домашку / в Сложные / в Упрощённые»,
                 стрелки вверх/вниз внутри блока]
        ↓  PATCH /api/assignment-blocks/<id>/  {question_ids: [...]}

  [Опубликовать]  → POST /api/assignments/<id>/publish/  (draft → active, состав frozen)

/teacher/lessons/<id>/results         — матрица результатов
  GET /api/assignments/<id>/matrix/
    строки = ученики (из students урока), колонки = блоки, ячейка = 3/8 · 42 %
    клик по ячейке → карточка: raw_answer | эталон книги | verdict | кнопки
                      «верно / неполно / неверно» (POST /api/assignment-answers/<id>/review/)
    фильтр «только pending_review» — это очередь ручной проверки из блока 3
```

Новых экранов два, но список задач и фильтр — переиспользование логики `BookBankPage`:
тот же `GET /api/questions/` с фильтрами «Класс»/«Сложность», которые уже на проде с
9-го деплоя.

### 2.4. Экран (б): ученик

Сейчас у ученика **нет** ни одного эндпоинта назначений (`AssignmentViewSet` закрыт
`IsTeacherOrAdmin`), и в `frontend/src/pages/student/` страницы нет. Это не пробел
документации, а фактический объём работы этого блока.

```
/lessons            — «Мои уроки»: active, не отозванные, с обратным отсчётом due_at
  GET /api/my/assignments/            (queryset: students=request.user, status=active)
/lessons/<id>       — вкладки блоков: Классная | Домашка | Сложные | Упрощённые
  GET /api/my/assignments/<id>/       (блоки, задачи, прогресс по текущему блоку)
    карточка задачи: условие через FormattedText (KaTeX) — тот же конвейер, что банк
                     ответ: textarea + предпросмотр тем же FormattedText (редактора формул нет)
    POST /api/my/assignments/<id>/answer/   {question, raw_answer}  → upsert AssignmentAnswer
    POST /api/my/assignments/<id>/submit/   {block}                  → state=submitted
                                             → на выходе: verdict по блоку 3 + матрица + событие в GetCourse
 Feedback ученику:
    correct/incorrect — сразу (level1/CAS)
    pending_review    — «у преподавателя», без оценки и без ложного нуля
```

Требование «переключаться между доступными блоками» реализовано вкладками, а не
последовательной разблокировкой: `simplified` должен быть доступен сразу тому, кто
не тянет `homework`, иначе блок теряет смысл.

### 2.5. Состав учеников: где snapshot ломается

`question_ids` заморожен (решение автора), `students` — живой M2M. Пока назначений не
было, расхождение не всплывало. С матрицей оно всплывёт: ученик, добавленный после
публикации, не имеет attempts, и матрица покажет ему пустую строку, а удалённый —
исчезнет вместе со своими ответами. Решение (не в этой миграции, а в этой же схеме):
на `publish()` состав закрепляется в `AssignmentStudent(assignment, student, joined_at)`,
и матрица строится по нему. Пока же это надо считать, а не чинить молча: при добавлении
ученика в опубликованный урок его старые ответы никуда не деваются, просто строка
появляется без истории.

## 3. Блок 3. Сверка открытых ответов (правило «слову модели не верим»)

Канон — **всегда `Question.latex_answer` из базы** (то, что напечатано в книге и принято
приёмкой). Ничто другое — ни решение, ни ответ модели, ни `solution_latex` (в банке он
пустой, 0 строк) — эталоном не считается.

### 3.1. Уровень 1 — детерминированный нормализатор (0 ₸, порядка единиц мс)

`_score_open_answer(question, raw) -> (verdict|None, normalized, confidence)`. Работает
только со строками, никакого вызова наружу:

1. **Снять обёртку:** `$…$`/`$$…$$`, `\[ \]`, `\text{…}`, `\mathrm`, `\quad`/`\;`/`~`,
   markdown-шум (`**`, `\tag{}`) — часть логики уже есть в `plain_from_latex`.
2. **Хвост цепочки:** если в строке есть `=` и за ним остаётся числовое значение,
   канон — последний фрагмент (`$s = 2\pi\Delta R = 2575\text{ км}$` → `2575 км`).
   Без этого шага уровень 1 покрывает меньше трети банка.
3. **Числа:** `,` → `.`, `$4{,}5$` → `4.5`, `\cdot 10^{19}`/`E19`/пробе-запись → float,
   `2,4(09)` → периодическая (сравнивать как 2.40909…), `\%` → доля, `\approx` → толерантностный хвост.
4. **Единицы:** нормаль к канону СИ с кириллицей и латиницей (`м/с`, `км`, `Дж`, `моль`,
   `об/мин`, `рад/с`, `дм$^{2}$`), умножение/деление в строке единицы — как запись размерности.
   Сверка с единицей и без неё = `partial`, не `incorrect`.
5. **Простые рациональные и корни:** `\frac{a}{b}` → a/b, `\sqrt[n]{m}`, `-42\frac{2}{3}` →
   смешанное число; сравнивать с толерантностью (по умолчанию `max(0.005·|значение|, 1e-9)`,
   для ответов книги с явным округлением — отдельный допуск).
6. **Несколько величин:** разделитель `;`/`,`/`<br>` → мультимножество значений, сравнение
   как набора (260 дм²; 312 дм³), порядок не важен, но сопоставление идёт по единице.
7. **Словесный хвост:** из `давление увеличится в $4{,}5$ раза.` извлекается значение, а
   совпадение слов не требуется; наоборот — 249 строк с кириллицей, где значения нет
   («давление уменьшается»), они уходят выше.

**Что он закрывает — честно.** Цифра «92 строки числом или числом с единицей» — нижняя
граница (те, где вся строка является числом). С шагом 2 и шагами 3–6 охват существенно
больше, но **замером это не подтверждено**: правдоподобная оценка — 150–250 из 588
(≈ 25–40 %), потому что 370 строк содержат дробь или корень, а среди них точные
symbolic-ответы с буквами (`$\frac{R^3 \sqrt{6}}{4}$`, `$4\pi Q$`), которые в число не
сворачиваются никогда.

Перед тем как это считать «решением», нужен один cheap замер (он же станет регрессией):
скрипт-фикстура на 588 канонических строк, который печатает, сколько из них схлопываются
в одно значение на уровне 1, и печатает список тех, где нормализатор дал `None`. Делать
его надо делать по банковому срезу, а не по надуманным примерам.

### 3.2. Уровень 2 — символьная эквивалентность

Порядок внутри уровня 2 фиксирован, и он важнее самого уровня:

* **2a. CAS (SymPy) — первым и бесплатно.** `latex_parse(эталон)` и
  `latex_parse(ответ)` → `simplify(a - b) == 0` (для многозначных — поэлементно).
  Это детерминированно и потому доверяем: вердикт `correct`/`incorrect` выставляется
  самим движением, `judged_by='cas'`. Покрывает как раз класс «дробь или корень» (361)
  и «формула» (10), где ответ — выражение.
* **2b. Узкий LLM — только как подсказка.** Вызов с ровно двумя строками:
  `эталон из БД` и `ответ ученика`, температура 0, фиксированная схема:
  `{"equivalent": true|false, "why": "≤200 знаков"}`.
  Модель **не решает задачу**: условия ей не передаётся, и в промпте нет ни номера, ни
  книги. Вердикт модели никогда не становится итоговой оценкой — она пишет
  `judged_by='model_suggestion'` и `verdict='pending_review'`, а тренер в матрице
  видит её аргумент как подсказку рядом с эталоном. Это и есть «слову модели не верим»,
  перенесённое в схему данных: машина имеет право только предлагать.
  Вызов логгируется (prompt-версия, токены, `money`) — деньги в долларах, ставка
  пересчитывается отдельно; на сверку одного урока это доли цента, но молча оно
  происходить не должно.

### 3.3. Уровень 3 — задачи, короткого ответа у которых нет

В банк это 75 строк без `latex_answer` плюс 19 строк с текстом «доказать / выясни /
можно ли» (из них ответ есть ровно у одной — `#34906`). Правила:

* `latex_answer` пуст → **сверки нет**, задача идёт в `pending_review` на тренера/
  куратора сразу при сдаче.
* **Ложного нуля не бывает.** В `TestSession` открытая задача отсечена другим способом —
  гардом `answerable()` (`subjects/models.py:14`), потому что в тесте её нечем проверить и
  `_score_question` вернул бы 0. В уроке та же строка законна: ученик пишет решение, и
  задача без ответа — это «не проверено машиной», а не «не верно».
* Запрещено выставлять `verified`/оценку по такой задаче автоматом и запрещено
  додумывать ответ в базу: источник первичен («если нет в книге — значит нет»).
* Очередь ручной проверки — тот же экран матрицы с фильтром `pending_review`;
  решение тренера пишется в `verdict` + `judged_by='human'` + `reviewed_by`.

### 3.4. Баллы

`points` в банке = 1.0 у всех 663, то есть весов нет. Предложение: `points_max` блока
считается как сумма `question.points` (то есть 1 на задачу), а `points_earned` — по
`verdict` (`correct` = полный, `partial` = половина, `incorrect` = 0,
`pending_review` = не считается и **не портит процент** — в процентах блока такие задачи
 идут в знаменатель только после ручной проверки). Проценты в матрице и в GetCourse
 обязаны считаться по одному правилу, иначе витрина и выгрузка разойдутся.

## 4. Блок 4. Точка стыковки с GetCourse (#24 Блок 2 — только контракт)

Коннектора не пишем. Здесь только интерфейс, под который потом встанет задача.

```python
# ВХОД: ученик приходит из урока GetCourse по подписанной ссылке, без второго логина.
# GET /api/lesson/join?gc_uid=…&assignment_id=…&ts=…&sig=…
#   sig = HMAC_SHA256(GC_LINK_SECRET, f"{gc_uid}|{assignment_id}|{ts}")
#   проверка: |now - ts| <= 300 с, assignment активен, gc_uid привязан к аккаунту
#   (User.gc_uid — поле понадобится; fallback — email из claims)
#   результат: JWT этой платформы + 302 на /lessons/<assignment_id>
#   отказ: 403 и ни одного создания аккаунта — регистрация остаётся в GetCourse

# ВЫХОД: конец блока homework → событие, из которого процент уходит в Tech API.
# AssignmentSubmission.state = 'submitted'  →  строка в OutboxEvent
#   {type: "lesson.homework.completed",
#    gc_uid, assignment_id, external_key: "<assignment_id>:<student_id>",
#    percent: earned/points_max, total, correct, pending_review, occurred_at}
#   фон-задача: POST → либо hw.pmci.kz (как сейчас у чужих ДЗ), либо напрямую
#   GetCourse Tech API; idempotency = external_key; повтор при 5xx с backoff;
#   тела ответов учеников наружу не уходят — только число и процент.
```

Что этот контракт сознательно не решает: где живёт `GC_LINK_SECRET` (секрет на сервере —
его слово, как с ключом Gemini), какой `customField` в GetCourse принимает процент и кто
проставляет `gc_uid` в аккаунтах платформы. Без этих трёх ответов стыковка не начинается.
